## M1 上游适配模块

**职责**：把五个图站的 API 差异抹平，对外统一产出 `WorkCard/WorkDetail/UserProfile/CreatorProfile`；管理上游鉴权、R-18/AI 过滤、Cloudflare 兜底。
**业务目标**：任何站点能力变化只改本模块；上层（页面/队列/同步）只认统一模型。
**入口**：`dispatchFetch(op, input)`（upstream/dispatch.ts）/ `dispatchSocial`（由 `/api/source`、`/api/social` 调用）；`fetchMediaResponse(url, ...)`（upstream/media.ts，`/api/media`）。
**核心文件**（TD-01 拆分后）：upstream/pixiv.ts（413 行）、upstream/fanbox.ts（332）、upstream/booru-sites.ts（267）、upstream/media.ts（254）、upstream/dispatch.ts（69）、upstream/http.ts（58）+ upstream.server.ts 桶（9 行保持旧导入）；共享解析 booru.ts、pixiv-feed.ts、pixiv-search.ts、pixiv-profile.ts、sites.ts；固定样本回归 upstream/mapping.test.ts（8 例）。
**核心接口**：`FetchInput`/`FetchOk` 19 种 op 判别联合（types.ts:104-173）；`SocialInput/SocialOk`。
**核心数据结构**：WorkCard（浏览卡片）、WorkDetail（+pages/ugoira/pools/statistics）、WorkPage（image|file）。
**数据库表**：无直接（经缓存模块落盘）。
**外部依赖**：五图站 + undici/curl 出站 + media-gate。
**业务规则**：safeMode 三层过滤（源站参数 rating:g/mode=safe → 本地 xRestrict/sl/sexual/hasAdultContent → BLOCKED_TAGS）；isMasked/lo 内容永久屏蔽；hideAi（pixiv ai_type=1）；Danbooru Basic 凭据免人机验证 + 强制 curl（UA 绑定 gallery-dl/1.27.0，勿随手改，TD-13 注记）；Konachan 镜像回退（200+HTML 也回退，TD-11 ✅）；Pixiv 日榜未指定日期且当天未公布→自动回落昨天（JST）。
**正常流程**：见 FLOW/FP-1；调用链 `页面 → fetchSource → POST /api/source（withDataPlane）→ dispatchFetch → <site> 映射函数 → outboundFetch → JSON 归一化 → 缓存写回`。
**异常流程**：上游非 2xx→带状态码 Error→统一 400；Konachan 降镜像；Danbooru 403/HTML→「源站暂时拒绝访问」；related/pools 等增强信息吞错返空（可降级）。
**状态变化**：无（无状态模块）；唯一内态是 social 的 CSRF token 缓存。
**关键配置**：kami.config.json（throttle）、代理。
**风险点**：~~上帝模块（TD-01）~~ ✅ 已拆；~~200+HTML 盲区（TD-11）~~ ✅；~~翻页启发式脆弱（TD-12）~~ ✅（改用过滤前原始条数）。剩余：上游接口改版本身（R-01，靠固定样本测试快速定位）。
**修改注意**：新增 op 必须同时改 `fetchSchema`（source.ts）与 `FetchOk` 联合，typecheck 会强制穷尽；不要在映射函数里直接读 localStorage/cookie——凭据一律来自请求体参数。
**图**：MREL、FLOW-FP1、SEQ「浏览请求」。

## M2 出站代理与限速模块

**职责**：全部服务端出站 HTTP 的唯一漏斗：代理决策、连接池、curl 兜底、熔断、媒体并发闸、限速热载。
**业务目标**：用户挂代理时快（持久连接）且稳（兜底+熔断），不挂代理时零开销。
**入口**：`outboundFetch(url, init)`（curl-fetch.server.ts:232）；`probeProxy`；`getActiveProxy/saveProxyUrl`（proxy.server.ts）。
**核心文件**：curl-fetch.server.ts（298 行）、proxy.server.ts、proxy-url.ts、media-gate.ts、throttle.ts/server.ts。
**核心接口/常量**：`PROXY_POOL_FAIL_LIMIT=3`、`PROXY_POOL_KEEPALIVE=10min`、undici connect 15s / headers 45s / body 45s / connections 16；curl `--max-time 40`；`MAX_MEDIA_BYTES=48MB`；mediaConcurrency 默认 6（clamp 1-32）。
**数据结构**：`globalThis.__kamiProxyAgent`（Agent 单例）；`.data/proxy.json` + kami.config.json + process.env.KAMI_PROXY 三处同步。
**外部依赖**：系统 curl 可执行文件、undici。
**业务规则**：无代理→原生 fetch；有代理→池；失败计数 3→熔断窗口走 curl；Danbooru 一律 curl。
**正常/异常流程**：见 FLOW「异常分支专述」2/3。
**状态变化**：熔断计数器与窗口（进程内，重启归零）。
**关键配置**：throttle 按 mtime 热重载（throttle.server.ts:14-33）。
**风险点**：curl 不存在时兜底链失效（Docker 镜像需自带）；`tineye` 配置键被静默忽略（配置漂移，TD-13）。
**修改注意**：所有新出站代码必须走 `outboundFetch`，禁止直接 `fetch`（否则绕过代理与熔断）；改超时记得与 curl `--max-time` 对齐。
**图**：MREL、SEQ「出站请求管线」。

## M3 服务端缓存模块

**职责**：列表缓存（`.data/source`，30min）+ 媒体缓存（`.data/media`，7d）+ Next unstable_cache（1800s）三层，隔离源站抖动；目录水位治理。
**业务目标**：换 IP/换设备不重拉；封面秒开；「刷新」按钮可精确击穿；磁盘不无界。
**入口**：`readSourceCache/writeSourceCache`（source-cache.server.ts）、`readCachedMedia/writeCachedMedia`（media-cache.server.ts）、`noteCacheWrite`（cache-watermark.server.ts）。
**核心规则**：列表 key = sha256(op+参数+safe+hideAi+uid)，uid 取 pixivUserIdFromCookie（**不含 cookie 原文**）；媒体 key = sha256(源 URL)；媒体单文件 ≤8MB 才落盘；fanbox 域与搜图引擎域不落盘（isDiskCacheableMedia）；TTL 过期仅在「再次读到」时惰性 unlink；**水位**：每 50 次写惰性扫描，超水位（media 2GB / source 512MB，kami.config 可配）按 mtime 淘汰到 80%（TD-07/PER-1 ✅）。
**数据结构**：`.json`（列表）/ `.bin`+`.json`（媒体，json 存 type+at；MIME 魔数嗅探纠偏）。
**正常流程**：读→命中返回→miss 打上游→写回→返回（写时顺手记水位）。
**异常流程**：写失败静默（不阻塞响应）；读损坏按 miss 处理。
**状态变化**：无。
**关键配置**：TTL 常量硬编码（SOURCE_CACHE_TTL_MS / MEDIA_CACHE_TTL_MS）；水位在 kami.config.throttle.cache。
**风险点**：~~无容量上限（TD-07）~~ ✅ 水位上线；~~媒体层无 in-flight 去重~~ ✅ PER-4（inflightMedia 单飞）。
**修改注意**：改 key 结构会使旧缓存全部失效（可接受但要知晓）；新增「不落盘域名」要同时改 isDiskCacheableMedia 与 MEDIA_SUFFIXES。
**图**：数据流图（DFD）。

## M4 应用认证与访问闸模块（Better Auth + withDataPlane）

**职责**：纸匣自己的账号体系：注册/登录/会话；为数据面 API 提供统一访问闸（应用会话或 LAN 启动令牌）。
**业务目标**：换浏览器/设备恢复数据；LAN 内未配对设备无法访问任何数据面端点。
**入口**：`/api/auth/[...all]`（Better Auth handler）；客户端 `authClient`（auth/client.ts）；`requireDataPlaneAccess`（auth/data-plane.server.ts，经 `withDataPlane` 包装 10 个数据面路由）。
**核心文件**：auth/server.ts（自托管 Better Auth，邮箱密码单通道）、auth/verify.server.ts、auth/data-plane.server.ts、auth/isolation.server.ts、auth/lan-token.server.ts（启动令牌：文件 + 三通道校验）、auth/email-password.ts、auth/pglite-dialect.ts、next-route.ts。
**核心接口**：`authConfigured`（VITE_AUTH_ENABLED 非 "false"）；`getSessionUser()`；`requireDataPlaneAccess(request)`（同站校验 → 会话或令牌）；`assertSameSiteRequest`（Fetch-Metadata）。
**数据结构/表**：`user/session/account/verification`（PGlite 或 Neon）；cookie `kami-auth.session_token`（HttpOnly，**secure:false** 为 LAN http 取舍，SEC-06 观察）；本地形态签名密钥落 `.data/auth-secret.json`（与会话快照同生共死，重启不掉登录）。
**外部依赖**：PGlite/pg。
**业务规则**：email/password 恒开；auth 关闭态要求启动令牌（Authorization 头 / `?token=` / 配对 cookie 三选一，`<img>` 场景走 cookie，终端打印配对指引）；跨站 scripted 请求 403（Fetch-Metadata）；session_data 5min cookieCache。
**正常流程**：注册→authClient.signUp.email→user+account(credential)+session 三表→cookie；数据面请求→withDataPlane→闸→业务。
**异常流程**：401 UnauthorizedError / 403 CrossSiteRequestError 映射 JSON。
**状态变化**：会话生命周期由 Better Auth 管理。
**风险点**：~~runAuth 死代码（SEC-01 根因）~~ ✅ 已接线；~~PREVIEW_CLIENT_SECRET 硬编码（SEC-05）~~ ✅ 平台退出后删除；剩余 SEC-06（http 明文 cookie）维持观察。
**修改注意**：新数据面端点一律 `withDataPlane(handler)` 包装（app/api/*/route.ts 的既有模式）；cookie 属性改动会影响 LAN http 可用性。
**图**：SEQ「登录与同步」、STATE「会话」。

## M5 图站账号与会话模块

**职责**：多账号（≤8/站）管理、当前账号派生、HttpOnly 镜像 cookie、身份探测。
**入口**：zustand `useSettings`（accounts/activeAccountId）；`POST /api/sessions`；`POST /api/whoami`。
**核心文件**：store.ts:123-134（withActiveCookies 派生）、accounts.ts、session-cookies.server.ts、apply-session.ts、site-identity.server.ts。
**数据结构**：`Account {id,label,pixivCookie,fanboxCookie,pixivProfile,fanboxProfile}`（**明文**，localStorage `kami-settings`）。
**业务规则**：FANBOX 缺会话回退 Pixiv 会话；`PIXIV_SESSION_RE` 正则校验合法性；切换账号=切 queryKey=换缓存空间。

**核心数据结构**：单例 `job {status, frame, pixiv, fanbox, profiles}`；状态机 idle/launching/waiting/done/error。
**外部依赖**：puppeteer-core + 系统 Chrome（KAMI_CHROME/CHROME_PATH/PUPPETEER_EXECUTABLE_PATH + 平台默认路径 + Playwright 浏览器目录）。
**业务规则**：恒 headless；临时 profile 用完即删；只收合法格式已登录会话；pixiv 登录后跳首页二次确认；4 分钟 deadline；700ms 轮询 cookie。
**正常/异常流程**：见 FLOW/FP-2 与 SEQ「登录中转」。
**状态变化**：STATE「登录任务」。
**关键配置**：代理跟随全局配置（--proxy-server + authenticate）。
**风险点**：全局单例（单用户假设）；~~GET 无鉴权返回 cookie 明文（SEC-02）~~ ✅ 已过闸；headless 反检测参数可能随 Chrome 版本失效。

## M8 账号同步与备份模块

**职责**：把客户端全部状态按四段（settings/vault/lexicon/history）在服务端 user_sync_segments 安家；备份导出/导入复用同一结构（v2 可口令加密）。
**入口**：AccountSyncBridge（providers 挂载）、右上角账号入口、设置页手动同步/恢复/备份；`GET/POST /api/account/sync`。
**核心文件**：account-sync.ts（分段推拉 + KEK 管理）、crypto-box.ts（PBKDF2 210k + AES-256-GCM 同构容器）、backup.ts（BackupFile 组装/校验，v2 settingsCipher）、backup-client.ts、app/api/account/sync/route.ts（validateSegment 分段校验）、db-snapshot.server.ts。
**数据结构**：SegmentPayload = `{kind:"cipher", box: CipherBox}` 或 `{kind:"plain", data, credsOmitted?}`；BackupFile = settings + vault 目录（mergeVaultRecords 以 key 去重、incoming 覆盖）+ lexicon/catalog + history + proxyUrl，≤2MB/段。
**业务规则**：登录瞬间 ensureSyncKek（服务端 kdf_salt → PBKDF2 → KEK 只存 sessionStorage）；变化分段 POST；`remoteExportedAt > marker[segment]` 才应用；恢复后 5s 静默窗；**段级 LWW**；凭据合并不变量（密文无 KEK 跳过 / credsOmitted 保留本地 / 无 KEK 跳推 settings）。
**正常流程**：登录→派生 KEK→拉快照→按段应用→后续变化分段推。
**异常流程**：PGlite 快照 30s/500ms 双触发落盘；内容未变跳过写；**⚠ TD-19：分段表不在快照 TABLES 内，重启丢失**。
**风险点**：~~LWW 无合并 / payload 无校验 / settings 明文入库（TD-09/SEC-03/SEC-09）~~ ✅ 第三批全修；剩余 TD-19 快照缺口。
**修改注意**：新增需要跨设备的状态必须同时进 collectBackup 与 applySegment，否则「同步了但没恢复」；新增落库表要评估是否该进 db-snapshot 的 TABLES（TD-19 教训）。

**职责**：纸感设计系统的技术底座：瀑布流排版、动效、卡片比例、主题、图片代理组件、动图播放。
**核心文件**：masonry-flow.ts（packJustified 算法，274 行）、motion.ts（FLIP/playEnter，合成线程）、card-aspect.ts、theme.ts（271 行，含防 FOUC bootstrap 脚本）、proxied-img.tsx（懒加载+shimmer+指数退避重试 4 次+media-lane 车道）、media-lane.ts（全局 4 条图片加载车道，详情首图插队）、work-detail.ts（详情查询键/预取统一）、ugoira-player.tsx / ugoira.ts / ugoira-zip.ts / ugoira-meta.ts、hover-preview.tsx、image-lightbox.tsx、paper-fly.ts（入队纸片动效）。
**业务规则**：骨架必须同走 MasonryBoard（真图进来不跳）；`prefers-reduced-motion` 关全部动效；悬停 160ms prefetchWork（与详情页同一查询键，30s staleTime）、520ms 出预览；ugoira 进视口才拉 zip、重试 3 次、最后一发 cache:"reload"。
**风险点**：MasonryBoard 用 MutationObserver(data-aspect) 自适应，卡片若不写 data-aspect 会留空洞；动图全帧解码在主线程 canvas（长图内存压力）。
**修改注意**：新动画必须同时进 reduced-motion 白名单；不要给 left/top/width 做动画（AGENTS.project.md）。
