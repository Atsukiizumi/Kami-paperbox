## M1 上游适配模块

**职责**：把五个图站的 API 差异抹平，对外统一产出 `WorkCard/WorkDetail/UserProfile/CreatorProfile`；管理上游鉴权、R-18/AI 过滤、Cloudflare 兜底。
**业务目标**：任何站点能力变化只改本模块；上层（页面/队列/同步）只认统一模型。
**入口**：`dispatchFetch(op, input)` / `dispatchSocial`（由 `/api/source`、`/api/social` 调用）；`fetchMediaResponse(url, ...)`（`/api/media`）。
**核心文件**：`src/lib/upstream.server.ts`（1257 行）、booru.ts（411 行）、pixiv-feed.ts、pixiv-search.ts、pixiv-profile.ts、sites.ts。
**核心接口**：`FetchInput`/`FetchOk` 19 种 op 判别联合（types.ts:104-173）；`SocialInput/SocialOk`。
**核心数据结构**：WorkCard（浏览卡片）、WorkDetail（+pages/ugoira/pools/statistics）、WorkPage（image|file）。
**数据库表**：无直接（经缓存模块落盘）。
**外部依赖**：五图站 + undici/curl 出站 + media-gate。
**业务规则**：safeMode 三层过滤（源站参数 rating:g/mode=safe → 本地 xRestrict/sl/sexual/hasAdultContent → BLOCKED_TAGS）；isMasked/lo 内容永久屏蔽；hideAi（pixiv ai_type=1）；Danbooru Basic 凭据免人机验证 + 强制 curl；Konachan 镜像回退。
**正常流程**：见 FLOW/FP-1；调用链 `页面 → fetchSource → POST /api/source → dispatchFetch → <site> 映射函数 → outboundFetch → JSON 归一化 → 缓存写回`。
**异常流程**：上游非 2xx→带状态码 Error→统一 400；Konachan 降镜像；Danbooru 403/HTML→「源站暂时拒绝访问」；related/pools 等增强信息吞错返空（可降级）。
**状态变化**：无（无状态模块）；唯一内态是 social 的 CSRF token 缓存。
**关键配置**：kami.config.json（throttle）、代理。
**风险点**：上帝模块（见 TD-01）；200+HTML 盲区（TD-11）；翻页启发式 `items.length>=20/8` 脆弱（TD-12）。
**修改注意**：新增 op 必须同时改 `fetchSchema`（source.ts）与 `FetchOk` 联合，typecheck 会强制穷尽；不要在映射函数里直接读 localStorage/cookie——凭据一律来自请求体参数。
**图**：MREL、FLOW-FP1、SEQ「浏览请求」。

## M2 出站代理与限速模块

**职责**：全部服务端出站 HTTP 的唯一漏斗：代理决策、连接池、curl 兜底、熔断、媒体并发闸、限速热载。
**业务目标**：用户挂代理时快（持久连接）且稳（兜底+熔断），不挂代理时零开销。
**入口**：`outboundFetch(url, init)`（curl-fetch.server.ts:232）；`probeProxy`；`getActiveProxy/saveProxyUrl`（proxy.server.ts）。
**核心文件**：curl-fetch.server.ts（298 行）、proxy.server.ts、proxy-url.ts、media-gate.ts、throttle.ts/server.ts。
**核心接口/常量**：`PROXY_POOL_FAIL_LIMIT=3`、`PROXY_POOL_KEEPALIVE=10min`、undici connect 15s / headers 45s / body 45s / connections 16；curl `--max-time 40`；`MAX_MEDIA_BYTES=48MB`；mediaConcurrency 默认 6（clamp 1-32）。
**数据结构**：`globalThis.__kamiProxyAgent`（Agent 单例）；`.data/proxy.json` + kami.config.json + process.env.KAMI_PROXY 三处同步。
**外部依赖**：系统 curl 可执行文件、undici。
**业务规则**：无代理→原生 fetch；有代理→池；失败计数 3→熔断窗口走 curl；Danbooru 一律 curl。
**正常/异常流程**：见 FLOW「异常分支专述」2/3。
**状态变化**：熔断计数器与窗口（进程内，重启归零）。
**关键配置**：throttle 按 mtime 热重载（throttle.server.ts:14-33）。
**风险点**：curl 不存在时兜底链失效（Docker 镜像需自带）；`tineye` 配置键被静默忽略（配置漂移，TD-13）。
**修改注意**：所有新出站代码必须走 `outboundFetch`，禁止直接 `fetch`（否则绕过代理与熔断）；改超时记得与 curl `--max-time` 对齐。
**图**：MREL、SEQ「出站请求管线」。

## M3 服务端缓存模块

**职责**：列表缓存（`.data/source`，30min）+ 媒体缓存（`.data/media`，7d）+ Next unstable_cache（1800s）三层，隔离源站抖动。
**业务目标**：换 IP/换设备不重拉；封面秒开；「刷新」按钮可精确击穿。
**入口**：`readSourceCache/writeSourceCache`（source-cache.server.ts）、`readCachedMedia/writeCachedMedia`（media-cache.server.ts）。
**核心规则**：列表 key = sha256(op+参数+safe+hideAi+uid)，uid 取 pixivUserIdFromCookie（**不含 cookie 原文**）；媒体 key = sha256(源 URL)；媒体单文件 ≤8MB 才落盘；fanbox 域与搜图引擎域不落盘（isDiskCacheableMedia）；TTL 过期仅在「再次读到」时惰性 unlink。
**数据结构**：`.json`（列表）/ `.bin`+`.json`（媒体，json 存 type+at；MIME 魔数嗅探纠偏）。
**正常流程**：读→命中返回→miss 打上游→写回→返回。
**异常流程**：写失败静默（不阻塞响应）；读损坏按 miss 处理。
**状态变化**：无。
**关键配置**：TTL 常量硬编码（SOURCE_CACHE_TTL_MS / MEDIA_CACHE_TTL_MS）。
**风险点**：**无容量上限/LRU**，文件数无界（TD-07）；媒体层无 in-flight 去重，并发同 URL 会重复拉取。
**修改注意**：改 key 结构会使旧缓存全部失效（可接受但要知晓）；新增「不落盘域名」要同时改 isDiskCacheableMedia 与 MEDIA_SUFFIXES。
**图**：数据流图（DFD）。

## M4 应用认证模块（Better Auth）

**职责**：纸匣自己的账号体系：注册/登录/会话；为 `/api/account/sync` 提供身份。
**业务目标**：换浏览器/设备恢复数据；部署态可联邦到 Grok auth。
**入口**：`/api/auth/[...all]`（Better Auth handler）；客户端 `authClient`（auth/client.ts）；`requireUserId`（verify.server.ts:84-97）。
**核心文件**：auth/server.ts（257 行）、gate-session.server.ts、gate-identity.server.ts、isolation.server.ts、email-password.ts、preview.ts、pglite-dialect.ts。
**核心接口**：`getAuth()`（三态：部署/预览/关闭）；`getSessionUser(headers?)`；`assertSameSiteRequest`（Fetch-Metadata 同站隔离）。
**数据结构/表**：`user/session/account/verification`（PGlite 或 Neon）；cookie `kami-auth.session_token`（HttpOnly，**secure:false** 为 LAN http 取舍）。
**外部依赖**：Grok gate（部署态 JWT/jwks，5min 缓存）、PGlite/pg。
**业务规则**：email/password 恒开；auth 关+真库=fail-closed；bearer 与 cookie 双通道；session_data 5min cookieCache。
**正常流程**：注册→authClient.signUp.email→user+account(credential)+session 三表→cookie。
**异常流程**：401 UnauthorizedError；CSRF 由 Better Auth 内建。
**状态变化**：会话生命周期由 Better Auth 管理。
**风险点**：**`runAuth` 死代码**——除 sync 外无任何业务端点接线（SEC-01 根因）；PREVIEW_CLIENT_SECRET 硬编码（SEC-05）。
**修改注意**：给新端点加鉴权时用 `runAuth(request)`（勿再手写 requireUserId）；cookie 属性改动会影响 LAN http 可用性。
**图**：SEQ「登录与同步」、STATE「会话」。

## M5 图站账号与会话模块

**职责**：多账号（≤8/站）管理、当前账号派生、HttpOnly 镜像 cookie、身份探测。
**入口**：zustand `useSettings`（accounts/activeAccountId）；`POST /api/sessions`；`POST /api/whoami`。
**核心文件**：store.ts:123-134（withActiveCookies 派生）、accounts.ts、session-cookies.server.ts、apply-session.ts、site-identity.server.ts。
**数据结构**：`Account {id,label,pixivCookie,fanboxCookie,pixivProfile,fanboxProfile}`（**明文**，localStorage `kami-settings`）。
**业务规则**：FANBOX 缺会话回退 Pixiv 会话；`PIXIV_SESSION_RE` 正则校验合法性；切换账号=切 queryKey=换缓存空间。
**正常流程**：设置/中转写入 → store 更新 → syncSessions 发镜像 cookie → /api/media 服务端从 HttpOnly cookie 取凭据拉图。
**异常流程**：会话失效→上游 400/登出态→身份探测刷新头像；sanitizePixivCookie 丢访客令牌。
**风险点**：明文三连（localStorage + 请求体 + user_sync/备份，SEC-03）；镜像 cookie 只被 media 端点消费，主通道仍是 body 明文——HttpOnly 保护被架空。
**修改注意**：新增图站凭据字段要同步改 accounts、fetchSchema、sessionSchema、cookiesFromSettings、backup 五处。
**图**：MREL、SEQ「登录中转」。

## M6 登录中转模块（browser-login）

**职责**：用本机无头 Chrome 打开官方登录页，投屏到应用内，代用户输入，收割会话 cookie——「不用手动贴 Cookie」。
**入口**：`POST /api/login-browser`（start/cancel/input）、`GET ?frame=0|1`（轮询帧+快照）；UI：session-relay.tsx（canvas 画帧、事件回传）。
**核心文件**：browser-login.server.ts（561 行）、browser-login.ts（类型+Chrome 路径探测）。
**核心数据结构**：单例 `job {status, frame, pixiv, fanbox, profiles}`；状态机 idle/launching/waiting/done/error。
**外部依赖**：puppeteer-core + 系统 Chrome（KAMI_CHROME/CHROME_PATH/PUPPETEER_EXECUTABLE_PATH + 平台默认路径 + Playwright 浏览器目录）。
**业务规则**：恒 headless；临时 profile 用完即删；只收合法格式已登录会话；pixiv 登录后跳首页二次确认；4 分钟 deadline；700ms 轮询 cookie。
**正常/异常流程**：见 FLOW/FP-2 与 SEQ「登录中转」。
**状态变化**：STATE「登录任务」。
**关键配置**：代理跟随全局配置（--proxy-server + authenticate）。
**风险点**：全局单例（单用户假设）；GET 无鉴权返回 cookie 明文（SEC-02）；headless 反检测参数可能随 Chrome 版本失效。
**修改注意**：不要把 job 挪出模块级单例（多标签并发依赖互斥语义）；新增站点登录需要新的合法会话正则与确认页逻辑。

## M7 下载队列与纸匣归档模块

**职责**：把「想要」变成「落盘」：串行队列 → 取详情 → 收图（含 GIF 合成）→ 三层归档（用户文件夹 / IDB / 服务端 vault）→ 完整性巡检。
**入口**：`enqueueWork`（queue-runner.ts:98）；`resumeQueue`（app-shell 启动时）；`rescanFolderHashes`。
**核心文件**：queue-runner.ts、save-work.ts、persist-files.ts、folder-access.ts、file-hash.ts、download-path.ts、vault-store.server.ts（323 行）、vault-sync.ts、vault-index.ts、vault.ts（IDB）、vault-query.ts。
**数据结构**：QueueItem（types.ts:197-210）；VaultMeta（types.ts:212-230）；SQLite `works/pages` 两表（files/ 目录像素）。
**业务规则**：队列上限 80、单并发、项间 400ms；去重同 key；用户文件夹 > 应用内目录；路径模板占位符 + 非法字符清洗 + 拒 `..`；删除 IDB blobs 缺 meta 时猜 24 页。
**正常流程**：见 FLOW/FP-3。
**异常流程**：失败标 error（无自动重试）；刷新 resume；文件夹写非原子（巡检兜底）；服务端 put 先删后写（崩溃留孤儿，TD-08）。
**状态变化**：STATE「队列项」。
**关键配置**：pathPreset/pathTemplate、vaultMirrorFolder/downloadToFolder、folderLabel（句柄存 IDB kami-folder）。
**风险点**：进度高频 patch 全卡片重渲染（PER-2）；vault 页无虚拟化（PER-3）。
**修改注意**：AGENTS.project.md 铁律——下载/入纸匣必须 enqueueWork，禁止旁路另存；动图失败回退链（GIF→zip）不要打断。
**图**：FLOW-FP3、SEQ「归档」、STATE「队列项」。

## M8 账号同步与备份模块

**职责**：把客户端全部状态打包成 BackupFile JSON，在服务端 user_sync 表安家；备份导出/导入复用同一结构。
**入口**：AccountSyncBridge（providers 挂载）、设置页手动同步/恢复/备份；`GET/POST /api/account/sync`。
**核心文件**：account-sync.ts、backup.ts（319 行）、backup-client.ts、app/api/account/sync/route.ts、db-snapshot.server.ts。
**数据结构**：BackupFile = settings + vault 目录（mergeVaultRecords 以 key 去重、incoming 覆盖）+ lexicon/catalog + history + proxyUrl，≤2MB。
**业务规则**：4s 防抖推；`remoteExportedAt > marker.syncedAt` 才应用；恢复后 5s 静默窗；整载荷 LWW。
**正常流程**：登录→拉快照→应用→后续变化防抖推。
**异常流程**：PGlite 快照 30s/500ms 双触发落盘；内容未变跳过写。
**风险点**：LWW 无合并（多设备互相覆盖）；payload 无 schema 校验（TD-09）；settings 含明文 cookie 入库（SEC-03）。
**修改注意**：新增需要跨设备的状态必须同时进 collectBackup 与 applyBackup，否则「同步了但没恢复」。

## M9 反向搜图模块

**职责**：一次上传并发问 SauceNAO/ascii2d/IQDB，聚合分组展示。
**入口**：`POST /api/reverse-search`（multipart：file≤8MB、safe、apiKey≤80）；`/search` 页。
**核心文件**：reverse-search.server.ts（306 行）、reverse-search.ts（解析器）、reverse-search-guard.ts（限速）、prepare-search-image.ts（浏览器缩图）。
**业务规则**：限速间隔 saucenao 8s（有 key ≤2.5s）/ascii2d 15s/iqdb 6s（kami.config 可调）；isBotChallenge 识别风控；hide=0（hide=3 会藏真匹配）；safeMode 过滤 e/q 结果；loli/shota 丢弃。
**正常流程**：预处理→三引擎 Promise.all→各解析器→按 site:workId 去重→workFromUrl 反解站内跳转。
**异常流程**：单引擎失败不炸整体；SauceNAO >12s 报错引导换 IQDB；limit 报错映射「今日次数用完」。
**风险点**：HTML 解析器对上游改版脆弱（与 upstream 同理）；ascii2d 会话 jar 8min 可能被上游缩短。

## M10 标签系统模块

**职责**：booru 英文 tag 的中文显示与输入联想：三层词表 + 词频收集。
**入口**：`displayTag/displayBooruTag`（site-tags.ts）、`tagSuggest` op、设置→词表。
**核心文件**：tag-lexicon.ts、tag-database.ts、tag-catalog.ts、tag-suggest.ts、site-tags.ts、src/data/booru-database.json（~119KB 打包数据）。
**数据结构**：词条 `{en,zh,ns,count}`，命名空间 general/copyright/character/artist/circle/meta；合并优先级 用户译文 > BUILTIN_TAG_LEXICON(~100 条) > 打包库；用户 zh 空串=删除该键。
**业务规则**：**显示用中文、请求仍发英文**（AGENTS.project.md 铁律，Pixiv/FANBOX 不套词表）；词频目录 8000 上限、400ms 批量 flush；联想合并序：已保存>最近>源站补全，截 10 条。
**风险点**：打包库静态陈旧（需人工更新 json）；catalog 无淘汰（长期被冷门 tag 占满 8000 槽）。

## M11 浏览 UI 基础设施模块

**职责**：纸感设计系统的技术底座：瀑布流排版、动效、卡片比例、主题、图片代理组件、动图播放。
**核心文件**：masonry-flow.ts（packJustified 算法，274 行）、motion.ts（FLIP/playEnter，合成线程）、card-aspect.ts、theme.ts（271 行，含防 FOUC bootstrap 脚本）、proxied-img.tsx（懒加载+shimmer+指数退避重试 4 次）、ugoira-player.tsx / ugoira.ts / ugoira-zip.ts / ugoira-meta.ts、hover-preview.tsx、image-lightbox.tsx、paper-fly.ts（入队纸片动效）。
**业务规则**：骨架必须同走 MasonryBoard（真图进来不跳）；`prefers-reduced-motion` 关全部动效；悬停 160ms prefetch 详情、520ms 出预览；ugoira 进视口才拉 zip、重试 3 次、最后一发 cache:"reload"。
**风险点**：MasonryBoard 用 MutationObserver(data-aspect) 自适应，卡片若不写 data-aspect 会留空洞；动图全帧解码在主线程 canvas（长图内存压力）。
**修改注意**：新动画必须同时进 reduced-motion 白名单；不要给 left/top/width 做动画（AGENTS.project.md）。
