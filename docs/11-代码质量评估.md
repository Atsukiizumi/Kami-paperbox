## 11.2 面向对象设计（SOLID 视角，按 JS/TS 语境）

项目是**函数式+模块**风格，不用类——本身合理。按意图对照：

- SRP：lib 模块普遍单一（好）；**例外是 UC 与 store.ts**（设置+队列+账号+cookie 派生多职责）。
- OCP：新增站点需要改 UC 的 switch/分支（对扩展需改已有文件），判别联合只保证 typecheck 穷尽，不保证开闭。
- LSP/ISP：不适用（无继承体系）；类型接口（Sql、LoginJob）窄而清晰。
- DIP：`Sql` 抽象（PGlite/Neon 可替换）是教科书式 DIP；出站层 outboundFetch 同理。**没做 DIP 的**是 vault（node:sqlite 直用）与缓存（fs 直用）——可接受，替换动机弱。

## 11.4 异常处理

- **吞异常面大**：UC 内 8+ 处 `catch { /* ignore */ }`（多为增强信息降级：related 返空、pools 返空、profile 补查放弃）；写缓存静默失败。降级意图合理但**无一保留原因日志**——排障时上游真实错误不可见。
- **错误转换粗暴**：/api/source 把一切（上游 5xx、限流、参数错）统一 400 + 拼接 message；upstreamJson 不解析 Pixiv 错误 message（UC:155-161）。
- **客户端**：乐观更新失败回滚（好）；queue 失败 toast + 状态保留（好）；ProxiedImg 指数退避 4 次（好）。
- 建议：服务端加一个极简 `console.warn("[upstream:op] cause")` 约定即可显著改善可观测性，不必引入日志库。

## 11.6 并发/异步模型

单进程 Node 事件循环 + 客户端 react-query。关键点：

- **队列单飞**（running 标志防重入，queue-runner.ts:82-96）——无锁需求。
- **单例竞态防护到位**：PGlite 初始化用 globalThis promise 防 HMR 双实例（db.ts:50-54）；CSRF token 用 in-flight promise 单飞（social.server.ts:19-30）。
- **异步无竞态防护**：vault.tsx:52-76、rankings.tsx:65-80 快速切换筛选时旧响应可能覆盖新响应（无 AbortController/token）——单用户低频操作，风险低但真实。
- **PGlite 单连接排队**（LazyPGliteDriver.acquireConnection 队列）——写并发天然串行化。
- 未发现死锁/线程安全问题（无 worker/线程 API）。

## 11.7 总体判断

**高于典型个人项目水准**：类型纪律（strict + 判别联合穷尽）、崩溃安全设计（原子写、快照、fail-closed）、Cancellation 处理、注释质量都达到小团队工程标准。主要扣分项：上帝模块集中度、异常可观测性（吞噬无日志）、死代码/过时注释存量、以及测试清单漂移这类「工程流程」而非「代码本身」的问题。
