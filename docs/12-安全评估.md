# 12 — 安全评估

## 12.1 威胁模型（先明确前提）

系统设计前提是「单用户、自己机器、可信局域网」。但**默认配置绑 `0.0.0.0:8080`**（kami.config.example.json:2、proxy.server.ts:97，README 明示手机/平板从 LAN 访问是特性），因此威胁模型必须覆盖「同局域网内存在不可信设备」。以下按此模型评级。

| 资产 | 位置 | 暴露面 |
| --- | --- | --- |
| 图站会话（PHPSESSID/FANBOXSESSID/Danbooru key） | localStorage、请求体、HttpOnly cookie、user_sync.payload、备份 JSON、login-browser 响应 | 高 |
| 纸匣内容（图片/目录） | /api/vault、.data/vault | 高 |
| 出站通道（可被劫持指向恶意代理） | /api/proxy | 高 |
| 应用账号库 | PGlite/快照 | 中（本地文件） |
| 上游流量（含凭据） | undici/curl + 用户代理 | 中 |

## 12.2 安全问题清单

> **2026-09-11 访客层注记（SEC-01 修订）**：应用账号开启但未登录的访客现可使用「公开内容面」——source（浏览/榜单/搜图数据）、media（图片）、social、reverse-search、rankings 只读；凭据由访客浏览器随请求体自带，不落服务端。个人面（vault 读写、sessions、login-browser、account/sync）与账号关闭形态（LAN 令牌）不变。残余风险：局域网内匿名设备可把本服务当上游代理用（带宽/IP 消耗）；Fetch-Metadata 同站校验仍生效，外站无法借受害者浏览器调用。个人自部署形态接受此暴露，公网部署应保持账号开启并留意。
> 状态（2026-09-10 两批修复后）：SEC-01 ✅ SEC-02 ✅ SEC-07 ✅ SEC-10 ✅（数据面 10 路由统一 `withDataPlane` 闸）；SEC-05 ✅；SEC-09 ✅（分段版校验）。第三批（docs/17）：SEC-04 ✅（queryKey 凭据指纹 + browse-cache v2 弃旧存储）、SEC-03 ✅（备份文件 v2 口令加密 + 同步设置段 KEK 加密；localStorage 设置项的收敛属长期方案未动）。剩余：SEC-06 / SEC-08 维持观察。

| 编号 | 问题 | 位置 | 严重等级 | 影响 | 修复方案 |
| --- | --- | --- | --- | --- | --- |
| SEC-01 | **数据面 API 全部无鉴权**：`runAuth`/`assertSameSiteRequest` 已实现但零调用；仅 /api/account/sync 与 /api/auth 有鉴权 | auth/middleware.ts:34（死代码）；src/routes/api/*.ts 全部 | **严重**（LAN 场景） | 局域网任意设备可：读写删纸匣（vault 四方法）、PUT/DELETE 热榜、POST /api/sessions 覆盖 cookie、启动/操纵登录中转、改代理指向 | 所有端点统一包 `runAuth(request)`；应用账号开启时强制登录，关闭时要求 query/header 携带启动时生成的随机令牌（打印在终端/二维码），无令牌拒绝 |
| SEC-02 | **登录中转 GET 无鉴权返回会话明文**：LoginJobSnapshot 含 pixiv/fanbox 会话串 | login-browser.ts:61-65、browser-login.ts:34-35 | **严重**（LAN） | 受害者中转登录完成瞬间，局域网攻击者轮询 GET 即可拿走图站账号 | 快照响应剥离凭据字段（前端在 done 事件里经带鉴权通道单独取）；或直接并入 SEC-01 的令牌方案 |
| SEC-03 | **图站凭据明文全链路**：localStorage `kami-settings`、/api/source body、user_sync.payload、备份 JSON | store.ts:163-180、accounts.ts:10-17、account/sync/route.ts:65-72、backup.ts:29-52 | 高 | XSS 或拿到任一落点即整串窃取会话；备份文件外发即泄露 | 短期：备份/同步 payload 对凭据字段做口令派生加密（WebCrypto PBKDF2+AES-GCM，导出时询问口令）；长期：凭据只存服务端 HttpOnly cookie，body 不再携带 |
| SEC-04 | **cookie 泄入第二存储**：首页 queryKey 含完整 cookie，browse-cache 把 queryKey 连同数据写 localStorage `kami-browse-v1`，且会被备份收集 | index.tsx:129,167、browse-cache.ts:89-102、backup.ts:4 | 高 | 敏感面扩大（清了设置也清不掉的 cookie 残留） | queryKey 用 cookie 哈希或账号 id；persistableQuery 剥离凭据段 |
| SEC-05 | **preview client secret 硬编码源码** | auth/preview.ts:20-21 | 中 | 持源码者可冒充 preview client（自称低权限可轮换，但无轮换机制） | 移到 env；或在部署形态禁用 preview provider |
| SEC-06 | **会话 cookie secure:false**（LAN http 取舍，代码注释自认） | auth/server.ts:220-223 | 中 | 明文 http 链路上 kami-auth.session_token / kami_* 可被窃听 | 文档明示风险；可选支持自签 https（`node --tls` 或反代）供高敏环境 |
| SEC-07 | **/api/proxy 可篡改出站指向**（与 SEC-01 同根但值得单列）：改 proxy = 全部带凭据上游流量过攻击者代理 | proxy.server.ts:127-153 | 中（LAN） | 凭据中间人 | 并入 SEC-01；另：保存代理时校验目标非回环/内网可选加严 |
| SEC-08 | SSRF 防线认知偏差：isPrivateIp 正则不覆盖 IPv6 映射/十进制字面量/解析到内网的域名；实际安全靠域名白名单 | upstream.server.ts:110-133 | 低（当前） | 若日后放宽 MEDIA_HOSTS 白名单立即暴露 | isPrivateIp 改为解析后判断（dns.lookup + net.BlockList）；注释标明白名单才是主防线 |
| SEC-09 | sync payload 无 schema 校验（只验 exportedAt） | account/sync/route.ts:57-63 | 低 | 恶意大 payload（≤2MB）污染 user_sync | 复用 backup zod schema |
| SEC-10 | vault/rankings 磁盘写入无路径遍历审计（相对 key 拼路径）；key 来自客户端 | vault-store.server.ts:193-199 | 低 | key 含 `../` 理论可越目录（PUT 时 key 经 zod 校验格式 `source:id`——【基于源码推导】已限字符集，需复核 id 白名单） | 在 put/get 前显式断言 key 匹配 `^[a-z]+:[A-Za-z0-9_-]+$` |

**已做对的部分**（对照参考）：Danbooru Basic 凭据只走 HttpOnly cookie；代理输出打码密码；curl 参数数组无 shell 注入；CSRF token 自动重取；Fetch-Metadata 同站隔离已全量接线（withDataPlane 第一步就是 assertSameSiteRequest）；XSS 面小（无 dangerouslySetInnerHTML 依赖外部输入的路径【基于源码推导】）。
