# 17 — 备份与同步加密设计（SEC-03 / TD-09）

> 2026-09-10 第三批设计稿，**两刀均已实施**（2026-09-11 复核：crypto-box.ts / backup.ts / account-sync.ts / 0003 迁移 / sync 路由分段校验全部落地，含 96f2768 两处冒烟修复——派生密钥可导出、iter 校验收数字字符串）。
> 目标：凭据（图站会话、Danbooru key、代理密码）在「离开本机内存」的每个落点都是密文——备份文件、服务端同步存储、磁盘。

## 威胁与落点

| 落点 | 威胁 | 对策 |
| --- | --- | --- |
| 备份 JSON 外发 / 云盘 | 拿文件即得会话 | v2 格式：设置 + 代理地址整段 AES-GCM 密文（口令派生） |
| `.data` 同步存储（user_sync） | 磁盘 / 快照文件泄露 | 同步分段化后，凭据段同样加密（第二刀） |
| localStorage 设置 | XSS / 本机其他进程 | 属「长期方案：凭据只走服务端 HttpOnly」，本批不动 |

## 加密原语（src/lib/crypto-box.ts）

- PBKDF2-HMAC-SHA256，210,000 轮，随机 16B salt（每容器独立）
- AES-256-GCM（自带完整性，口令错 = 解密失败）
- WebCrypto 原生，Node 22 / 浏览器同构，可单测

## 第一刀：备份文件 v2（已实现）

- `kami-paperbox-backup-v2`：与 v1 同构，`settings` + `proxyUrl` 可整体替换为
  `settingsCipher`（CipherBox 容器）；vault / 词表 / 历史保持明文（目录性数据）
- 导出：设置 → 备份新增可选「导出口令」；留空 = 明文 v1（旧行为零变化）
- 导入：检测到 `settingsCipher` 先问口令；v1 永远直接导入
- 服务端 `/api/account/sync` 的 parseBackup 校验对密文文件返回明确错误（不误存）

## 第二刀：账号同步分段 + 登录派生密钥（✅ 已实施）

- **分段（TD-09/18）**：`user_sync` 单行整载荷 → `user_sync_segments`
  （settings / vault / lexicon / history 四段，各自 exportedAt，LWW 粒度到段）
- **密钥**：KEK = PBKDF2(应用账号密码, user_sync_meta.kdf_salt)。salt 由服务端
  首次 kdf-salt 请求时随机生成固定下发；KEK 只放 sessionStorage（不落盘）。
  - 登录/注册瞬间（密码在手）：派生 KEK → 拉取解密 → 全量推送（含加密凭据段）
  - 长会话（cookie 存活、KEK 不在）：偏好类分段照常明文推送；settings 段推送时
    标记 `credsOmitted`（凭据字段真的不上服务端），拉取侧合并规则 = **远端新但缺凭据 → 保留本地凭据**
  - 拉取遇密文且无 KEK：跳过 settings 段（本地凭据不动），其余段照常
  - 推送守卫：无 KEK 且服务端 settings 已是密文时**跳推 settings 段**（防 omit 段把密文凭据冲掉）
- **换设备语义不变**：新设备登录（输密码）→ 派生 KEK → 拉取解密恢复全部
- migration `0003_user_sync_segments.sql`：分段表 + meta 表；旧单行数据由
  拉取侧兼容读取，首次推送后自然迁移

## 已知缺口（TD-19，2026-09-11 新发现）

`db-snapshot.server.ts` 的 TABLES 清单（user/account/session/user_sync）**未包含
本设计的两张新表**——PGlite 形态（本机 / Docker 默认）重启后分段数据与 kdf_salt
丢失。修复见 14 文档 TD-19；修前该设计的服务端持久化在本地形态下不成立。

- vault / 词表 / 历史加密（非敏感目录数据）
