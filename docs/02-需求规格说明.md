# 02 — 需求规格说明（逆向还原）

> 本项目无正式需求文档；以下功能需求由页面、路由、API 与数据结构逆向还原。CHANGELOG 是事实上的需求变更记录（Keep a Changelog 格式，每条对应 PR）。

## 2.1 系统解决的问题

用户在浏览器直接访问图站有三类痛点：**访问不稳定**（Cloudflare 拦截、直连超时，需代理）、**凭据管理繁琐**（手动贴 Cookie 易失效）、**收藏无处安放**（原图散落、跨设备不同步）。Kami 纸匣的解法是把「访问源站」整体搬到用户自己的服务端（带代理、缓存、凭据），把「收藏」落成本地文件夹 + 应用内归档 + 账号同步三层。

## 2.2 业务角色

| 角色 | 定义 | 依据 |
| --- | --- | --- |
| 访客（未登录任何账号） | 浏览 Pixiv 全年龄榜单、三个 booru 站帖子、标签搜索、以图搜图 | README.md:50；upstream 可选 cookie 的端点 |
| 图站登录用户 | 在访客能力之上：Pixiv 推荐/关注流/R-18 榜/红心收藏关注、FANBOX 首页/订阅/付费内容 | README.md:51 |
| 应用账号用户 | 图站登录用户之上：设置跨浏览器/设备同步（纸匣自己的邮箱密码账号） | CHANGELOG「应用账号」条目 |
| 运行者（部署者） | 配置代理、限速、数据目录、备份恢复；即用户本人（单用户自托管是设计前提） | kami.config.json、settings 页 |

无 RBAC、无多租户——单用户自托管是显式设计前提（登录中转全局单例等实现均以此为基础）。
