# 07 — 接口设计说明

> 两类接口：**本站 API**（浏览器 ↔ 本站，`app/api/**` → 实现 `src/routes/api/**`）与**上游 API**（本站 → 源站，映射表）。全部 Route Handler 均 `runtime=nodejs` + `force-dynamic`，经 `withRequest` 包装（Request 入 AsyncLocalStorage）。

## 7.1 本站 API 清单

| 路径 | 方法 | 请求参数 | 返回 | 鉴权 | 上游 | 缓存 | 业务含义 |

## 7.3 接口设计评价

**优点**：单一 `/api/source` 出口 + zod 判别联合 = 自文档且类型穷尽；`/api/media` 统一代理解决防盗链与混合内容；错误面小（客户端只需处理 400/401/网络层）。

**问题**：

| 问题 | 说明 | 建议 |
| --- | --- | --- |
| 无版本控制 | 路径无 /v1；客户端与服务端同仓部署故风险低，但浏览器端旧缓存（localStorage 的 react-query 数据）与新服务端格式若不兼容会静默出错 | FetchOk 已是判别联合，可加 `v` 字段 |
| 错误码粗糙 | /api/source 把一切错误统一 400（source.ts:43-46），上游 5xx/限流/参数错不可区分 | 至少区分 502（上游）与 400（参数），透传上游 message |
| 重复语义 | cookie 双通道（body 明文 + HttpOnly 镜像）并存，media 用后者、source 用前者 | 收敛到 HttpOnly 通道（见 16 路线） |
| 凭据在 GET 之外明文过 body | 见 12 安全评估 | 同上 |
| RESTful 程度低 | 全 POST 的 RPC 风格 + GET 有副作用的 login-browser 轮询 | 单体内可接受，无需整改 |
| 幂等 | social 写操作天然幂等（on 布尔）；sync upsert 幂等；无需去重令牌 | 维持 |
