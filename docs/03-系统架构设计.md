# 03 — 系统架构设计说明

## 3.1 架构模式

**客户端-服务端一体的模块化单体（Modular Monolith, CSR-heavy）**，非 MVC/MVVM/Clean/DDD/微服务。具体形态：

- **一套 Next.js 进程同时承担** Web 服务器（静态壳 + App Router 路由）与 **BFF/反向代理**（全部源站访问都发生在服务端，浏览器只与本站通信——这是本项目最重要的架构决策，解决了代理、防盗链、Cloudflare、凭据四类问题）。
- **UI 层重客户端渲染**：`app/` 页面全是 `"use client"` 薄壳，真实组件在 `src/routes/`；数据获取全部走 react-query + fetch，SSR 只负责主题 bootstrap 与 HTML 壳（app/layout.tsx:19-38）。
- **分层但无领域层**：UI → API 网关（zod 校验）→ 上游适配（服务）→ 基础设施（出站/缓存/存储）。没有 Repository 抽象、没有领域实体行为——`WorkCard/WorkDetail`（types.ts:24-76）是纯数据 DTO，业务规则（过滤、状态、路径模板）散布在服务函数与工具模块中。
- **双持久化体系**：SQL 型数据（应用账号/同步）走 `Sql` 抽象（PGlite/Neon 双后端，db.ts:32-41）；文件型数据（纸匣/缓存/热榜）直接落盘 SQLite/JSON/二进制，不经过 `Sql`。
- **客户端是第一公民**：下载、GIF 编码、路径模板、文件夹写入都发生在浏览器（利用 FS Access API 与用户磁盘直连），服务端反而只是「可选兜底」——这与常见「重服务端」架构方向相反，是刻意的（README「纸匣优先记用户文件夹路径」）。

## 3.2 分层分析

| 层 | 实际位置 | 说明 |
| --- | --- | --- |
| UI / Presentation | `src/routes/*.tsx`、`src/components/**` | 页面组件 + 业务组件 + shadcn 基础件；`app/**` 仅薄壳 |
| Application（客户端编排） | `src/lib/source.ts`、queue-runner、save-work、account-sync、backup-client | react-query 之外的用例编排，全部在客户端 |
| API 接口层 | `app/api/*/route.ts` → `src/routes/api/*.ts` | `withRequest` 把 Request 放进 AsyncLocalStorage（next-route.ts）供 cookie/认证读取 |
| Service（上游适配） | upstream.server.ts、booru.ts、pixiv-*.ts、social.server.ts、reverse-search.server.ts | 端点映射 + 数据归一化 + 上游鉴权 |
| Infrastructure | curl-fetch（出站）、proxy.server（配置）、throttle、media-gate、browser-login.server | 进程级资源（连接池、Chrome、限速闸） |
| Persistence | db.ts（PGlite/Neon）、vault-store/ranking-store（node:sqlite）、source-cache/media-cache（文件）、db-snapshot（JSON） | 无统一 Repository；每类数据自选存储 |
| External Integration | 五个图站、三个搜图引擎、Grok gate/connectors（未用） | 全部经服务端出站 |

## 3.3 架构质量评价

**优点（高内聚的证据）**

1. **出站统一漏斗**：所有源站流量收敛到 `outboundFetch` 一个函数（curl-fetch.server.ts:232-277），代理/熔断/兜底只需在一处实现；Danbooru 强制 curl 等特例也在此表达。
2. **单一 /api/source 出口 + zod 判别联合**：19 种 op 在 `fetchSchema` 强类型穷尽（source.ts:20-115），客户端与服务端共享同一 schema，接口漂移会被 typecheck 拦截。
3. **缓存分层职责清晰**：浏览器 localStorage（首屏）→ react-query 内存（30min）→ Next unstable_cache（1800s）→ `.data/source`（30min）→ 源站，每层 TTL 与失效路径明确（browse-cache.ts 头注释）。
4. **薄壳迁移策略**：`app/` 只 re-export `src/routes/*`，框架迁移（TanStack→Next）没有污染业务组件；`kami-link.tsx` 保留 TanStack 风格 API 包一层 Next Link。
5. **崩溃安全设计有据**：PGlite 拒绝 dataDir（上游缺陷 #327）改用 JSON 快照 + tmp/rename 原子写（db-snapshot.server.ts:87-101）；fail-closed 的 `requireUserId`（auth 关 + 真库 = 拒绝降级 dev user，verify.server.ts:86-91）。

**问题与风险**

| 问题 | 位置 | 影响 |
| --- | --- | --- |
| 上帝模块 | upstream.server.ts 1257 行，混杂端点映射、数据映射、媒体代理、缓存头、Cloudflare 兜底 | 每新增一个站点/端点都改同一个文件，merge 冲突与回归面大 |
| 鉴权层存在但未接线 | `runAuth`/`assertSameSiteRequest`（auth/middleware.ts:34、isolation.server.ts:38-56）零调用者 | 数据面 API 全部裸奔（详见 12 文档 SEC-01），架构意图与实现脱节 |
| 三代框架遗留并存 | server/middleware（Nitro）、grok-pwa-plugin（Vite）、check:auth 依赖已消失的 `/__app-env` 端点 | 死代码维护成本、检查工具名存实亡、误导新维护者 |
| 客户端单飞队列与浏览器存储强耦合 | queue-runner.ts:19,82-96 | 队列只活在单个标签页；关页即停，刷新靠 resumeQueue 补救 |
| 类型检查覆盖不全 | tsconfig include 只有 `src/app/next.config.ts`（tsconfig.json:39-45），`scripts/`、`server/` 无类型检查 | 工程脚本与平台中间件的质量裸奔 |
| 循环依赖风险低但横向依赖随意 | lib 内互相 import 较自由（如 upstream ↔ booru/pixiv-*） | 无 lint 边界约束，演进中容易劣化 |

**架构优化方向**（详见 16 文档）：拆 upstream.server 为 `adapters/<site>/`；为数据面 API 统一挂 `runAuth` + 可选局域网令牌；清理三代遗留；把「单用户自托管」写成显式的架构假设文档。
